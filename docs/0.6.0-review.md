范围：文本阅读、本地导入、来源兼容、书架、订阅、同步与升级。漫画、TTS 不在计划内。本轮仅审查并记录，没有修改业务代码。

## 开发落实（0.6.0-beta.1）

本节记录用户授权开发后的结果，下文保留开发前审查的原始证据与建议。 后续性能与冗余代码改进另见 `docs/0.6.0-performance-improvements.md`，该文记录本轮最终测试及包体验证。

- 已修复订阅源分组、排序、图标与转换版本的备份遗漏，兼容旧备份缺键，也保留显式清空分组的语义。
- 同步改为用同一次 GET 返回的强 ETag 条件上传；首次创建也带创建条件。冲突最多重试三次，每次重新下载并拍本地快照。同步标记只采用 GET/PUT 自身响应中的版本，不再使用上传后 HEAD。
- 净化规则与订阅源落库时在写事务内重读最新行；设置在一次 DataStore edit 内裁决、完整写入并保存远端时间戳。设置导出从同一份磁盘快照取值与时间戳，本地编辑时间戳严格递增。
- 前台正文、预取、显式刷新与图片写缓存均校验请求开始时的缓存代数；清理后的请求使用新代数，不再加入尚未完成的旧请求。
- 损坏或不受支持版本的备份会保留原文件并报告失败，不再自动覆盖。无强 ETag 的已有备份可拉取，暂停覆盖上传；依赖服务器正确执行条件请求。旧客户端或网页版若仍盲写，并不自动获得本轮并发保护。
- 通用净化仍采用现有抓取阶段处理，本轮补充编辑与删除提示，指向阅读菜单的“重新获取本章”；没有改变字符偏移和旧缓存格式。
- 启用 Room schema 导出，留档 v22；应用注册与迁移测试共用同一条迁移链。新增 v1→v22 真实 SQLite 升级测试，核对书籍、章节、进度、订阅数据及当前列/索引结构。保留历史 v11→v12 清空旧格式来源的既有行为。
- 新增 `ReaderBenchmark.repeatedPageTurns` 的帧耗时测量入口，使用已有本地 txt 夹具；已更新历史性能报告的过时结论。

## 结论

建议将 0.6.0 定位为“数据可靠性与阅读稳定性”版本。当前最值得投入的是同步完整性、并发写入保护、旧数据升级验证和真机阅读回归。没有足够证据支持全面重写阅读器、替换架构或继续普遍性性能重构。

版本号本身不是必须跨到 0.6.0：如果只修少量问题，继续发 0.5.10 也合理；如果要集中补齐同步协议和发布门槛，单独开一个 0.6.0 周期有明确价值。不要为了版本号补新功能。

## 需要优先处理的问题

### 1. P1：订阅源同步丢失分组，并可能重置本机附属字段（确定缺陷）

位置：`core/.../webdav/BackupPayload.kt:70`；`app/.../data/repo/WebDavRepository.kt:329`；`app/.../data/db/entity/RssSourceEntity.kt`。

`BackupRssSource` 没有 `groupName`、`sortOrder`、`icon`、`converterVersion`。同步接收端又不是复制已有实体，而是用构造器创建新实体后 upsert，这些字段会落成默认值。尤其分组是可由用户独立编辑、且不回写 JSON 的真实数据：`RssRepository.setGroup` 的注释明确这一点。因此另一设备无法恢复用户分组，远端启停等更新被采纳时，还会清掉本机已有分组。图标、转换版本等字段的后续表现需按订阅类型验证。

处理：明确哪些字段跨设备同步、哪些保留本机值；备份补齐应同步字段，导入端基于已有行 copy。旧备份缺字段时应有“未提供”的兼容语义，避免把缺字段误当成用户清空分组。

验收：A 设备自定义分组 → B 同步后相同；B 关闭订阅源 → A 同步后分组和图标不丢；旧备份导入不会清空现有分组。

### 2. P1：多设备同时同步可覆盖对方刚上传的数据（并发缺陷）

位置：`WebDavRepository.syncLocked` 的 GET → merge → PUT；`core/.../webdav/WebDavClient.kt:60`。

`syncMutex` 只串行化本进程。客户端 PUT 没有条件头，也没有冲突重试。A、B 都读取远端 R，分别合并自己的修改后上传，最后一次 PUT 会覆盖第一次 PUT 中只存在于另一设备的修改。若另一设备继续同步，部分数据可能重新带回来；不能保证永久丢失，但远端在此期间不完整，设备丢失或清数据会扩大影响。

此外，PUT 后单独 HEAD 再保存版本标记仍有窗口：若 B 恰在 A 的 PUT 与 HEAD 之间上传，A 可能将尚未合并过的 B 版本记成“已同步”，后续自动同步跳过。

处理：将内容与版本标识绑定读取；服务器支持时用强 ETag 的条件 PUT，首次创建使用对应创建条件；冲突后重新 GET、合并并有限重试。上传后的标记必须来自本次写入可证明对应的版本，不能无条件采信随后 HEAD。缺少可靠条件写入能力的服务器需有明确兼容策略，不能声称完全消除了多设备冲突。

验收：用 MockWebServer 控制两个客户端交错请求，两边新增、删除、进度更新都保留；模拟条件失败重试；模拟 PUT/HEAD 之间第三方写入，不能误记已同步。

### 3. P1：同步写回规则、订阅与设置时，可能覆盖本地较新的修改（并发缺陷）

位置：`WebDavRepository.kt:320`、`:329` 及事务后设置导入；`AppPrefs.importFromBackup`；`ReaderPrefs.importFromBackup`。

书目和来源已经在写事务中重读最新行，再按时间戳裁决；净化规则与订阅源直接把合并快照 upsert。若用户在拍快照后、事务写回前删除或禁用一条，旧合并结果会覆盖这笔操作。设置导入同样没有在实际提交处比较最新时间戳；阅读设置还通过多次更新写入并最终回填远端时间戳，存在中间状态和本地修改被错误标旧的窗口。

处理：规则、订阅统一在写事务中重读裁决；偏好设置在 DataStore 原子更新内部比较版本，一次提交完整设置及其时间戳。单纯在导入函数入口检查一次不足以关闭并发窗口。

验收：暂停同步在快照之后，执行本地禁用、删除、改分组或改字号，再继续同步，较新的操作必须保留。

### 4. P2：前台正文和图片写缓存没有统一使用失效代数（并发缺陷）

位置：`NetReaderBookSource.store`、`loadImage`；对照 `OfflineDownloader` 的 `epoch` / `writeIfEpoch`。

后台下载已经使用“开始请求时记录 epoch，落盘时检查”的保护。前台普通加载、预取和图片只检查 `cacheWritesHeld`，正文随后直接 `cache.write`。当请求尚未完成时用户清空缓存、远端同步换源或删书，旧请求仍可能在清理之后重新写入。布尔检查与实际写入之间也不是原子操作。阅读页主动换源有额外保护，但并没有覆盖所有清理入口。

处理：正文、手动刷新、预取、图片共享同一套缓存写入失效协议；请求开始时拍代数，清理与检查写入共用锁。目录缓存标记也要核对，避免只阻止文件写入却留下错误标记。

验收：用延迟响应启动加载 → 清理/换源/删书 → 放行响应，旧结果不能重新创建已失效缓存。新增图片路径也要测。

### 5. P2：网络书的通用净化规则修改后，旧缓存无法重新应用（已有行为限制）

位置：`ReplaceRuleRepository.purifyFor`；`ReaderViewModel.loadPurified`（约 1599 行）。

网络书通用净化在抓取阶段执行，缓存保存的是净化后的结果；阅读时只应用本书规则，刻意避免重复替换。结果是修改或关闭通用规则后，重新分页仍从已经净化过的缓存取数据，不能恢复被删文字；开启新通用规则也不能影响已有缓存，除非重新获取正文。本地书与本书专属规则走渲染阶段，因此行为不同。

处理：短期明确刷新入口和提示，通用规则改变后允许重抓受影响章节；长期评估“来源解析缓存 + 渲染净化”的分层方案。需保持字符偏移和阅读位置语义，不宜在本轮直接大改。

验收：缓存正文 → 开启/关闭/修改通用规则 → 明确验证当前章与后续缓存章节的行为；`a → ab` 之类非幂等替换不能重复执行。

## 设计风险与待验证项

- **坏备份自动覆盖**：`syncLocked` 将一般解码异常视为没有远端备份，随后用本地覆盖。这是明确写在代码中的自愈策略，但没有保留坏文件或上一份好快照，也未区分未来不兼容格式与损坏。建议保留可恢复副本、报告状态并对未来版本设保护。归类为恢复策略风险，不宣称所有解码失败都会丢数据。
- **用 MAX 时间戳作为本地变更版本**：它不是可靠的修订计数。除了时钟回拨，延迟提交且时间戳低于现有最大值、同毫秒写入，都可能不改变标记；未来时间戳也会长期掩盖其他修改。建议采用持久化修订号或可靠内容指纹，并覆盖写入入口。
- **阅读位置并发刷盘**：`flushProgress` 使用独立协程，需验证退出、后台、防抖写入与新会话交错时是否出现旧位置后提交。当前没有足够证据把它列为已确认用户可触发缺陷。
- **跨午夜阅读时长**：目前整笔时长按 record 时刻所属日期落库。若需要精确日统计，应验证跨日分段与单调时钟计时；优先级低于同步完整性。

## 历史问题哪些已解决、哪些仍欠账

已在当前实现看到的修复，不能重复列成未完成：

- 启动完整绘制上报：`BookshelfScreen.kt:206` 已有 `ReportDrawnWhen { shelfReady }`。历史性能报告中“完全没有上报”的结论已经过时。
- 同进程重复同步已有互斥；书目和来源同步落库已有新鲜度判断；书目同步换源会清本地目录和正文缓存。
- 正文文件缓存已有临时文件 + 原子替换；后台离线下载已有 epoch 防止清理后旧数据回写。
- 手动重新获取章节已有“抓取并排版成功后才提交”的路径和相关测试。
- 当前版本已有滚动快翻修复、目录变化对位和缓存标记批量处理等近期改进。需要回归验证，不据提交说明保证没有回归。

仍有价值的工程欠账：

- 数据库已经到 v22，但 `exportSchema = false`。现有迁移 SQL 单测有用，仍不能替代真实旧库升级并由 Room 校验最终结构和数据。建议保存 schema，并选代表性历史版本做升级测试。
- 基准模块目前只有启动计时与 profile 生成，没有独立的阅读帧耗时回归用例。补齐快翻、长章、带图、改字号重排、目录刷新与进出书场景。
- CI 会运行单测和 debug 构建，但自动化设备测试覆盖主要是 WebView；发布前仍需要阅读流程、升级和同步集成验证。
- `TextMeasurer(cacheSize = 0)` 仍在。它只是值得实验的参数，不是已证实性能问题；缓存可能增加内存，先比较命中率、分页耗时与峰值内存再决定。
- 历史性能报告需标注适用版本、关闭已完成项，避免下一轮照旧报告重复开发。

## 建议的开发周期

按一名熟悉项目的开发者、已有可用构建与测试环境估算：**10–15 个工作日，约 2–3 周**。这是工作量估算，不是基于团队实际速度的承诺；外部 WebDAV 兼容和设备问题可能延长。当前本机环境修复应先于验证开始。

| 阶段 | 工作量 | 交付与必要性 |
| --- | --- | --- |
| 问题固化 | 1–2 天 | 建立同步交错、RSS 字段保留、缓存失效回归用例；先证明问题，再定修复范围 |
| 数据可靠性修复 | 4–6 天 | 修复上列 1–4；处理旧备份兼容与冲突降级，避免修改再次损坏旧数据 |
| 升级与阅读回归 | 3–4 天 | 历史库升级、两设备同步、离线阅读、近期 0.5.9 功能真机验证；性能只处理量出来的退步 |
| Beta 与收敛 | 2–3 天 | 至少两个回归轮次，收集有触发步骤的反馈；不在冻结后追加大功能 |

若只修 RSS 字段映射和局部写回问题，可拆成较短的 0.5.x 修复版；多设备冲突协议、旧格式兼容和真实升级验证不应压缩成“改完编译过就发”。

## 0.6.0 发布门槛

1. P1 缺陷有可重复验证并修复；两客户端交错同步不静默覆盖，旧备份不清用户分组。
2. 净化规则、订阅和设置同步途中发生本地新修改，较新的修改能保留。
3. 清缓存、删书、换源后，迟到的正文和图片响应不能写回旧缓存。
4. 0.5.9 → 0.6.0 及选定历史版本升级保留书架、阅读位置、规则、订阅和设置；数据库结构校验通过。
5. API 33 和较新 Android 真机至少覆盖核心阅读；能取得设备时补低内存机、横竖屏/宽屏、后台回收恢复。
6. 滚动连续快翻、返回再进、离线已缓存书、重抓失败保留原文、移出后重新加入、图片开关与断网等场景回归通过。
7. 三模块单测、debug 构建通过；release 包安装运行抽查。记录测试设备、样本、版本与残留问题。

本轮明确不新增漫画、TTS；也不建议将 UI 重做、全量架构迁移或依赖整体升级塞入这一版本。
