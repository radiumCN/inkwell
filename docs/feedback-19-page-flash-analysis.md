# 反馈 #19：水平翻页闪屏

排查日期：2026-11-17。反馈版本：v0.5.9；本地基线：8e43bae（0.6.0-beta.4）。
反馈：<https://github.com/radiumCN/inkwell/issues/19>。

## 录屏证据

用户提供的 MP4 长约 5.18 秒，共 126 个解码帧。它是相册播放手机实拍视频的录屏，
不是应用直接录屏；实拍曝光、屏幕扫描与视频压缩可能产生混合画面，因此不能由它推算应用帧耗时。
下文时间取视频解码时间戳，帧号从 0 开始。

- 第 32、33 帧（1.318、1.359 秒）：下一页正文已基本占满阅读区域，页脚仍为 2/8。
- 第 34 帧（1.400 秒）：上一页正文重新出现在原位，并与下一页形成混合画面。
- 第 35、36 帧（1.441、1.482 秒）：恢复下一页，页脚更新为 3/8。
- 另一轮翻页在第 60–64 帧（2.471–2.635 秒）从 3/8 落到 4/8；第 62 帧也有混合画面，
  但不如第 34 帧明确，不能仅凭它认定同一故障再次发生。

最明确的现象是落页时旧正文短暂回闪，而不是只见全屏纸色或整体亮度波动。
动画呈水平移动，未见卷角；视频没有展示设置，不能单独确认持久化的翻页模式。
抽帧证据保存在本地 `tmp/feedback19/flash-evidence.jpg`，不提交包含用户正文的图像。

## 高度匹配的代码时序

`reader/.../flip/PageFlipContainer.kt` 中：

1. SLIDE/COVER 在组合阶段按 `direction` 选择静止页或双页动画图层。
2. 动画图层的 `graphicsLayer` 在延后的图层更新中读取 `offset.floatValue`。
3. 收尾原先调用 `resetFlipState()`，同时执行 `direction = null` 和 `offset = 0`。
4. `direction = null` 需要重组才能卸下旧图层；立即清零位移则可能先作用于仍存在的旧图层，
   使已经移出屏幕的旧页返回原位，直到静止页的组合提交。

这条时序与第 33 → 34 → 35 帧高度匹配，是本次优先修复的原因；录屏没有应用内部帧追踪，
仍不能把框架调度顺序或 MagicOS 专属行为当成已经实测证明的事实。
Compose 的分阶段状态读取机制见官方说明：
<https://developer.android.com/develop/ui/compose/phases>、
<https://developer.android.com/develop/ui/compose/graphics/draw/modifiers>。

已检查的反证与边界：

- v0.5.9 到本地基线，以上 reset 和 SLIDE/COVER 渲染路径没有实质变更，不能声称新版已经修好。
- `showPage()` 将当前页和邻页写入同一份状态；容器还通过 HeldPages 桥接提交后的短暂等待。
  这并不保证绘制时序正确，但不能简单归为“每次都先把当前页置空”。
- 本段从同章 2/8 翻到 3/8，不涉及章末网络加载，网络等待不是解释这次闪回的首选。
- `BrightnessEffect` 在亮度目标未改变时不写窗口属性；沉浸效果的 key 不含页码。
  没有证据表明每翻一页就重新设置亮度或开合系统栏。
- CURL 的异步位图切换及固定 32 ms 回收是其他候选路径，本段没有证据将其认定为根因。

## 本地修复

`resetFlipState()` 只结束方向与收尾状态；位移清零移到静止态的 `SideEffect`，
在成功应用组合、卸下动画图层后执行。新手势及程序化翻页依然自行设置初始位移。
不增加逐帧重组，不以固定延时猜测帧边界，也不做设备型号特判。

覆盖范围：SLIDE/COVER 正常提交、回滚和动画中断后的复位；CURL 的平移降级路径也共用该位移。
本改动不解决缺页加载、位图缓存或快速连续翻页可能存在的其他问题。

2. 对比原版与修复版，重点观察落页时旧正文是否重现；先单次松手等落定，再快速连续翻与反向打断。

4. 最好取得应用直接录屏或帧追踪；若仅实拍可见，结合曝光/刷新率条件继续区分呈现问题与拍摄伪影。
