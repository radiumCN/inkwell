# 0.6.0-beta.1 性能与冗余代码复核

日期：2026-11-16。对象：当前工作区（包含尚未提交的 0.6.0-beta.1 修改）。漫画、TTS 不在范围内。本文件保留开发前复核记录；审查阶段没有修改业务代码。用户授权后的落实情况见 `docs/0.6.0-performance-improvements.md`。

## 结论与优先顺序

有可执行的优化空间，最明确的是搜索排序的重复解析；另有批量导入重复全表读取、统计榜单逐条查书、订阅规则重复转换等结构性低效。当前没有真机帧数据，不对翻页、冷启动提升幅度作承诺。

建议顺序：搜索排序 → 清理未使用接口 → 大批量导入与统计查询 → 首次进书字体扫描 → RSS 解析缓存 → release 资源裁剪实验。阅读器文本测量和绘制缓存仍先量后改。

## 1. 搜索排序重复解析：建议优先优化

位置：`app/.../ui/search/SearchViewModel.kt:655–705`、`:904–941`。

按字数/更新日期排序的比较器，每次比较两个元素都重新遍历其所有来源，调用字数或日期解析函数。字数解析还在每次调用中创建最多三个 Regex；日期解析会遍历匹配并创建 Calendar。列表在搜索过程中每 250ms 最多发布一次，同一批不变的记录会再次参与排序。

现状的解析次数约为 O(来源数 × 结果数 × log(结果数))。对每条记录提前计算排序值，可把本轮解析次数降到 O(来源数 × 结果数)，排序比较只比较数字。SearchHit.results 不可变，后续还可评估跟随结果实例缓存排序值；需要避免改变排序稳定性、并发发布和数据更新语义。

### 本轮独立 JVM 对照实验

工具：`docs/performance/SortProbe.java`；原始结果：`docs/performance/sort-results.txt`。环境：本机 macOS arm64，Homebrew JDK 21。六轮预热，九轮取中位数，每本三个来源。

探针直接调用当前编译产物中的 `SearchViewModelKt.parseWordCount` / `parseUpdateEpoch`，对比“比较器内重复求值”和“排序前一次求值”。对同一输入检查两者输出顺序一致。

| 本数 | 排序 | 重复求值 | 提前求值 | 单轮解析次数变化 |
| --- | --- | --- | --- | --- |
| 500 | 字数 | 26.551 ms | 6.347 ms | 23064 → 1500 |
| 500 | 日期 | 18.784 ms | 1.176 ms | 23004 → 1500 |
| 2000 | 字数 | 115.207 ms | 12.143 ms | 116220 → 6000 |
| 2000 | 日期 | 84.300 ms | 4.085 ms | 116136 → 6000 |

边界：这是针对排序键计算的合成实验，不是运行完整 ViewModel 或真实 UI。它没有包含中文 Collator 的真实次级比较、网络、数据库、Compose 或手机性能；日期输入为每来源一个文本片段。实验能证明重复解析的计算成本和减少重复工作的收益，不能直接换算成手机帧率或整轮搜索提速倍数。排序当前已在 Default 线程，不能把上述时间称为“主线程卡住时长”。

复现示例（仓库根目录，先构建当前代码；JDK 与 Kotlin 缓存路径按本机调整）：

```sh
JAVA_HOME=/opt/homebrew/opt/openjdk@21 ./gradlew :app:bundleDebugClassesToCompileJar
```

随后使用 JDK 21 的 javac/java，classpath 包含 `app/build/intermediates/compile_app_classes_jar/debug/bundleDebugClassesToCompileJar/classes.jar` 和当前 `kotlin-stdlib-2.4.21.jar`，编译并运行 SortProbe。不要将开发机结果当作真机数据。

## 2. 批量导入每本书重复读取全书库：数据量大时值得优化

位置：`BookRepository.shelfLocalBookByKey:90`、`insertCopiedLocal:209`；`BookshelfViewModel.importBooks:639`。

多文件导入逐本调用 importLocalBook，每本在判重时调用 getAll（包含移出书架的记录），再在内存按类型与规范化书名/作者过滤。这会反复读取整行数据，包括简介、路径等判重不需要的列。

如果已有 1000 行，再成功导入 1000 本全新书，仅判重读取的行数约为 1000+1001+…+1999 = 1499500；这只是工作量推导，尚未计时，文件解析也可能仍占主要耗时。

建议：建立轻量判重投影/规范化索引，或批次开始加载索引、每成功导入更新索引，并在提交处复核并发变化。必须保留网络书与本地书的区分、移出后恢复、缺文件占位重新关联和阅读进度保留等语义。不能简单以文件名重复为由跳过 EPUB。

## 3. 阅读统计榜单逐条查书：条件性的 N+1

位置：`ReadingStatsViewModel.kt:37–61`。

统计先取全年所有书的排序结果，再逐本 getById，找到五本非隐藏书才停。普通情况是五次查询；前排隐藏书或书行已不存在时，最坏会逐条查完今年读过的全部书。

建议：批量获取候选书的标题/作者/隐藏状态，再选前五；或在数据库侧完成适当关联。隐藏书时长仍必须计入总时长，隐藏书不能出现在榜单，不能通过“只统计可见书”偷省工作。收益尚未实测，优先级低于搜索排序。

## 4. 字体导入限制检查太晚，首次实例化还同步扫描目录

位置：`ReaderFontStore.kt:35`、`:55–59`、`:91`；`AppModules.kt:58`、`:147`。

- 字体最大 64MB 的限制在 input.copyTo 完整复制之后才检查。误选一个数 GB 且后缀为 ttf 的文件，会先读写完整文件，随后才删除并报错。应在复制循环达到上限后立即停止；读取有限长度而非事后计数。这里跑在 IO，不等于会直接阻塞主线程，但会浪费时间和磁盘写入。
- ReaderFontStore 构造时 `_fonts = MutableStateFlow(scan())` 同步列目录并检查文件。ReaderViewModel 直接注入它，首次从 UI 创建、且没有其他后台路径提前创建时，会在主线程执行扫描。目录通常很小，实际影响未测；建议 IO 预热或异步加载，并确保本机字体可用性判断不会因初始空列表而错误回退。

## 5. RSS 规则可按内容缓存，避免启停/分组变化重解整组

位置：`RssRepository.ruleOf:61`；`RssTimelineViewModel.catalog:75`；`RssSourceViewModel.webSourceIds:42`。

订阅源表变化后，时间线会重新解析全部启用源。转换版本旧的条目还会每次重新转换 sourceJson。该转换故意不写库以免污染同步时间戳，但可以按 json/sourceJson/转换器版本缓存派生规则，把启停单独覆盖。仅改分组不应重解所有 JSON。

现有小说来源仓库已有解码缓存，不能把它和 RSS 一概说成“所有来源每次都重解”。缓存需有限容量，内容变更后正确失效。尚未量化收益。

## 7. Android Lint 结果

本轮 `:app:lintDebug` 成功：25 条 warning，没有 error。离线首次执行因 Lint 专用依赖未缓存而失败，下载后完整检查通过。

- 4 条 StaticFieldLeak：这几个 ViewModel 目前均通过 Koin androidContext() 注入 Application Context，不能据此认定 Activity 泄漏。
- NotShrinkingResources：release 开启代码压缩，未开启资源裁剪。可比较开启后的 release APK 大小与资源完整性，收益尚未测。全部图标方案均有业务入口，不能因图标多就当作无用资源删除。
- AutoboxingStateCreation：Motion.kt:170 使用 mutableStateOf(Float)，可换 mutableFloatStateOf；低成本清理，但系统动画倍率不是高频逐帧更新，预计不会成为体感瓶颈。
- 其余包括 Modifier 接口约定、v26 资源目录冗余、KTX 写法和依赖版本提示。依赖升级提示不等于存在性能 Bug，不在本轮直接升级。

报告：`app/build/reports/lint-results-debug.html` 与 SARIF 同名文件。

## 8. 当前不应直接改的性能候选

- TextMeasurer(cacheSize = 0)：没有本轮实验支持改成非零；扩大缓存会增加 TextLayoutResult 持有内存。
- refreshNeighbors：当前已通过 samePage 比较避免无变化时发布状态；历史报告中“每次无条件整树刷新”的描述不适用于当前实现。showPage 仍会构造当前及相邻页外壳，是否值得缓存要量绘制和分配后再决定。
- 卷页位图：已有后台渲染、请求合并及旧图复用，不应重新并发构造整页位图。
- 主分页、本地文件读取、网络抓取的主要路径已有 Default/IO 调度。没有找到可以据此宣称“应用普遍在主线程读大文件”的证据。

本轮没有连接真机，未测实际冷启动、帧耗时、耗电、峰值内存与 release 资源裁剪收益。上述建议中的结构性工作量证据与独立 JVM 数据，应与这些尚未测量的体验指标区分。
